2. The 7 ER-to-Relational Mapping Rules

Rule ER Construct Relational Transformation Applied in FlashDrop
Rule 1 Strong Entity Sets Direct relation creation with simple attributes. Designate PK (users, products, drops).
Rule 2 Weak Entity Sets Include partial key + owner PK as composite foreign key with ON DELETE CASCADE (order_items, wallet_ledger).
Rule 3 1:1 Relationships Place PK of one entity as foreign key with UNIQUE constraint in child table (wallets.user_id UNIQUE, inventory.drop_id UNIQUE).
Rule 4 1:N Relationships Place PK of "1" side as foreign key in "N" side relation (products.category_id, orders.user_id).
Rule 5 M:N Relationships Resolve using associative bridge relation with composite foreign keys (lottery_entries, user_tiers).
Rule 6 Recursive / Unary Add foreign key referencing same relation's PK (categories.parent_id, referrals.referrer_id).
Rule 7 Multi-Valued Attr Modeled using native MySQL 8 JSON typed column (products.attributes_json for size/color).

2. Step-by-Step Normalization Proofs

1. First Normal Form (1NF): All attributes have atomic domain values. Non-atomic attributes (e.g. shipping street, city, state, postal) are decomposed. No repeating groups exist.

2. Second Normal Form (2NF): Must be in 1NF and contain zero partial dependencies. In composite bridge relations (order_items, user_tiers), non-prime attributes functionally depend on the entire candidate key, not a proper subset.

3. Third Normal Form (3NF): Must be in 2NF and contain zero transitive dependencies (X → Y and Y → Z). For instance, orders stores user_id, but does NOT store email or customer_name, which transitively depend on user_id.

4. Boyce-Codd Normal Form (BCNF): A relation is in BCNF if for every non-trivial functional dependency X → Y, X is a superkey. Because every table uses unique candidate keys and surrogate primary keys, every determinant is a superkey.

3. Examiner Viva Defense Q&A (Component 2)

Q1: What is the exact difference between 3NF and BCNF?
Answer: 3NF permits a dependency X → Y if Y is a prime attribute (part of a candidate key), even if X is not a superkey. BCNF removes this relaxation: every determinant X MUST be a superkey without exception. FlashDrop satisfies BCNF across all 20 tables.

Q2: Did you denormalize any tables? Why?
Answer: In inventory, we store available_quantity alongside total_allocated, reserved_holds, and sold_quantity, strictly protected by the database check constraint: CHECK (available_quantity + reserved_holds + sold_quantity = total_allocated). This deliberate denormalization eliminates expensive COUNT(*) aggregation queries over the massive orders and order_items tables during sub-millisecond stock checks.
