2. Step-by-Step Normalization Proofs

Normal Form Theoretical Requirement Application & Verification in FlashDrop Schema
1NF (First NF) All attributes contain atomic values; no repeating groups or multivalued arrays. All fields are atomic. Multi-part attributes like addresses are decomposed into address_line1, city, state, postal_code.
2NF (Second NF) Must be in 1NF; zero partial dependencies (all non-prime attributes depend on full candidate key). In composite bridge tables (order_items, user_tiers), non-key columns depend on the entire composite key.
3NF (Third NF) Must be in 2NF; zero transitive dependencies (no non-prime attribute depends on another non-prime attribute). In orders, customer attributes (email, first_name) are excluded to prevent order_id → user_id → email transitive dependency.
BCNF (Boyce-Codd) For every non-trivial dependency X → Y, X must be a superkey without exception. Across all 20 relations, every determinant is a candidate key or superkey. The schema completely satisfies BCNF.

3. Examiner Viva Defense Questions & Answers

Question 1: What is the formal difference between 3NF and BCNF?
Answer: 3NF permits a functional dependency X → Y if Y is a prime attribute (part of any candidate key), even if X is not a superkey. BCNF strictly eliminates this relaxation: every determinant X must be a superkey. FlashDrop uses surrogate primary keys and candidate keys across all 20 tables, satisfying BCNF.

Question 2: Did you introduce any controlled denormalization?
Answer: Yes, in table inventory we store available_quantity alongside total_allocated, reserved_holds, and sold_quantity, protected by a MySQL check constraint: CHECK (available_quantity + reserved_holds + sold_quantity = total_allocated). This eliminates costly runtime COUNT(*) aggregation queries during high-concurrency stock checks.
