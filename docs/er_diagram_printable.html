1. Identifying Relationships & Weak Entity Lifecycles

Parent → Child Entity Relationship Type Semantic Rationale & Referential Cascade Invariant
orders → order_items Identifying Weak Entity An order_item has no semantic validity outside its parent order. Enforces ON DELETE CASCADE so orphan line items cannot exist.
wallets → wallet_ledger Identifying Weak Entity Every ledger entry is an immutable delta strictly tied to a parent wallet. A balance change without an owning wallet violates double-entry principles.

2. Examiner Viva Defense Questions & Answers (Component 01)

Question 1: What is the difference between a strong entity and a weak entity in your ER model?
Answer: A strong entity possesses an independent existence with a primary key derived entirely from its own attributes (e.g., users, products, drops). A weak entity depends existence-wise on an identifying owner entity; it has no independent existence and its lifecycle is bound to the owner (e.g., order_items cannot exist without orders; wallet_ledger cannot exist without wallets).

Question 2: How did you resolve Many-to-Many (M:N) relationships in your model?
Answer: In relational theory, M:N relationships cannot be modeled directly with single foreign keys. We decomposed M:N relationships using associative bridge entities: users × drops in the fair waiting room is decomposed via lottery_entries with UNIQUE(drop_id, user_id), and users × loyalty_tiers is decomposed via user_tiers.

Question 3: Why are categories self-referencing instead of having separate subcategory tables?
Answer: Creating separate tables (e.g. subcategories, sub_subcategories) introduces fixed depth and schema rigidity. A unary self-referencing relationship (parent_id → category_id) enables arbitrary hierarchical tree depth in a single normalized table, queryable via standard ANSI SQL Recursive CTEs.

Question 4: Why is inventory modeled as a separate 1:1 entity rather than an attribute of drops?
Answer: Drops represent marketing event schedules (start, end, status), while inventory represents the physical durable stock core under high-frequency pessimistic row locks (available_quantity, reserved_holds, sold_quantity). Separating them isolates row-locking overhead from event metadata and allows the in-database check constraint CHECK (available + reserved + sold = total).
